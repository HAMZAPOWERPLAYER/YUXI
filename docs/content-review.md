# Kana Content Review

**Status:** content complete, **not yet approved for release**
**Applies to:** `src/features/kana/data/` (208 kana records)
**Reviewers required:** a Japanese-language teacher and a native Urdu speaker

Every kana table and Urdu pronunciation hint is flagged `needsHumanReview: true`.
The data is structurally complete and covered by automated tests, but structure is not
the same as correctness. This document defines the review scope, the checks to perform,
and the sign-off needed before publishing the app.

Coverage is deliberately limited to the 46 basic kana, the 20 dakuten + 5 handakuten
kana, and the 33 common yōon combinations per script. Rare or obsolete forms
(`ゔ`, `ゐ`, `ゑ`, `ヷ`, `ヸ`, `ヹ`, `ヺ`, `ヿ`) and small-vowel loanword combinations
(`ファ`, `ティ`, `ヴァ`, …) are **out of scope** for this milestone. Adding them later
requires new records, not edits to existing ones.

The flags live in:

- each of the six data-set files above;
- `src/features/kana/data/index.ts` (`needsHumanReview`, and the aggregate JSON export);
- the `KanaDataSet` type in `src/features/kana/data/buildKana.ts`.

`buildKanaJsonExport()` / `serializeKanaJsonExport()` in `data/index.ts` produce a plain
JSON view of all 208 records for reviewers or for a future content pipeline. The app
itself does not ship that JSON file; the TypeScript tables are the source of truth.

## Record model

Each record is generated by `buildKana` from a compact seed tuple. The generated fields
are:

| Field            | Example                           | Reviewed?                  |
| ---------------- | --------------------------------- | -------------------------- |
| `id`             | `hiragana-shi`                    | Yes — stability rule below |
| `script`         | `hiragana`                        | Yes                        |
| `group`          | `basic`                           | Yes                        |
| `kana`           | `し`                              | **Yes — most important**   |
| `romaji`         | `shi`                             | **Yes**                    |
| `row`            | `s`                               | Yes                        |
| `urduHint`       | `شی`                              | **Yes**                    |
| `confusableWith` | `['hiragana-sa', 'hiragana-chi']` | Yes                        |
| `ttsText`        | `し` (derived from `kana`)        | No — generated             |

`ttsText` is always a copy of `kana`, so audio never disagrees with the glyph. If a
reviewer changes a glyph, the spoken text changes with it.

## Japanese review checklist

- [ ] **Glyph accuracy:** every character is the intended hiragana or katakana, not a
      kanji, half-width form, or lookalike from the other script.
- [ ] **Script separation:** hiragana files contain no katakana and vice versa.
- [ ] **Romaji system:** Hepburn-style readings, applied consistently:
      `shi` (not `si`), `chi` (not `ti`), `tsu` (not `tu`), `fu` (not `hu`),
      `ji` (not `zi`), `sha`/`cha`/`ja` (not `sya`/`tya`/`zya`).
- [ ] **Special kana:** `を` is `wo`, `ん` is `n`. Confirm that the beginner-facing
      choices are acceptable even though `を` is normally pronounced `o` as a particle.
- [ ] **Yōon forms:** the base kana and the small `ゃ` / `ゅ` / `ょ` are correct, and no
      combination is written with a full-size vowel. Confirm the expected set of 33 per
      script (11 base rows × 3 vowels) and that omitted archaic combinations are
      intentionally absent.
- [ ] **Dakuten / handakuten:** the 20 voiced kana and 5 semi-voiced `p` kana are
      correct, including `ぢ` / `づ` and `ヂ` / `ヅ`.
- [ ] **Row labels and ordering:** `vowels`, `k`, `s`, `t`, `n`, `h`, `m`, `y`, `r`,
      `w`, `n-final`, and the yōon rows (`ky`, `sh`, `ch`, …) group the records the way
      the charts display them.
- [ ] **Confusable pairs:** each suggested pair is genuinely easy to mix up for a
      beginner, references an existing id, and is not one-sided (if A lists B, B should
      usually list A). The list is illustrative, not exhaustive.
- [ ] **TTS check on a device:** listen to a sample of basic, dakuten and yōon entries.
      The device voice should read the kana, not spell out romaji.

### Known items that need a decision

1. **`ぢ` / `づ` romaji.** The data uses `dji` / `dzu` to keep ids unique against
   `じ` / `ず`. The visible `romaji` field also says `dji` / `dzu`, which is a teaching
   choice rather than standard Hepburn (`ji` / `zu`). Reviewers must confirm or change
   this, and if changed, keep the ids stable (see below).
2. **`を`.** Shown as `wo`. Decide whether the hint and romaji should acknowledge the
   particle pronunciation `o`.
3. **`ん`.** Shown as `n` in the `n-final` row and grouped separately so it is not
   confused with the `na` row.
4. **`ふ`.** The Urdu hint is a description (“between ف and ہ”) rather than a single
   letter because Urdu has no exact equivalent. Confirm it is understandable.
5. **`ら` row.** Hints offer both `ر` and `ل` because Japanese /r/ sits between the two.
   Confirm the dual hints are helpful rather than ambiguous.
6. **Yōon Urdu hints.** Several use a short vowel (`کیا`, `شا`, `چا`) while others use
   explicit diacritics (`کِیُو`). Confirm a consistent, natural style.

## Urdu review checklist

- [ ] Hints are natural Urdu for Urdu-medium learners, not English transliteration or
      Persianized pronunciation.
- [ ] Vowel length and diacritics are consistent: `ا` / `آ`, `ی` / `ے`, `و` / `او`,
      and short vowels where needed.
- [ ] Consonants that do not exist in Japanese are not implied: no retroflex `ٹ`/`ڈ`/`ڑ`
      unless explicitly explained, and no Urdu letter that changes the sound.
- [ ] `ہ` vs `ح` vs `خ`, `ش` vs `ژ`, and `چ` are used consistently with the Japanese
      sound.
- [ ] The hints read well in the app at every text size, in Noto Nastaliq Urdu, without
      clipped diacritics or broken joining. Check the kana detail screen, quiz feedback
      and charts; these use different type scales.
- [ ] No hint is empty, duplicated by accident, or contains Latin text mixed into Urdu
      copy. Explanatory parentheses (such as `فو (ف اور ہ کے درمیان)`) are acceptable
      only if they render correctly.
- [ ] Confusable-pair hints do not rely on the Urdu hint alone; the visual glyph is the
      main cue.

## ID stability rule

Record ids are generated as `<script>-<seed id>`, for example `hiragana-shi`,
`katakana-kya`, `hiragana-dji`. They are **persistent user data**, not display labels:

- `kana_progress.kana_id` and `review_log.kana_id` store them;
- spaced-repetition state, due dates and mastery are keyed by them;
- backup files contain them;
- chart, detail and quiz routes use them.

**Before the first public release,** ids may still be corrected, because no real user
data exists. After release, renaming an id silently would orphan that kana's progress
and review history. If a rename is unavoidable later, add a migration that rewrites
`kana_progress` and `review_log` rows (and bump the backup format) instead of editing
the seed alone.

Also keep the hiragana/katakana pair aligned: `hiragana-shi` and `katakana-shi` should
represent the same sound. A structural test enforces uniqueness, not semantic pairing;
the reviewers must confirm the pairing.

## How to review

1. Read the six seed files. The compact tuples are intentionally easy to scan:
   `[id, kana, romaji, row, urduHint, confusableWith?]`.
2. Compare each row against a trusted kana reference (for example the kana charts from
   the Japan Foundation or a standard dictionary).
3. Open the app's Learn → chart and kana detail screens to see the content in context.
   Check both languages (Urdu and English), all three text sizes, and both scripts.
4. Record every change as a seed edit, not as a runtime override.
5. After edits, run:

   ```bash
   npx tsc --noEmit
   npm run lint
   npm test
   npm run check:network
   ```

   The data tests verify count, uniqueness, script/group consistency, confusable
   references, romaji/id pairing and JSON round-trip. They cannot verify linguistic
   correctness.

6. Re-run the app and spot-check the changed records in a quiz, including Listening
   mode, to confirm TTS and feedback still read the right glyph.
